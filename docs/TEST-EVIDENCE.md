# Test evidence

## 15 October 2026: Windows x64 development machine

Rust 1.99.0, MSVC Build Tools 2022, bundled libcurl reporting 8.22.0-DEV with Schannel and HTTP/2 capability, nghttp2 1.68.1 and SQLite. Exact versions are recorded in Cargo.lock. The official rustup installer was downloaded into a workspace-local tools directory; no global PATH changes were required.

`cargo test --workspace --locked --offline`: 9 unit tests passed. Cases cover URL redaction/protocol rejection, device/stream filenames, DPAPI round trip, range bounds, changed resource identity, ignored ranges, publication recovery, rejection of unrelated identical files and conservative handling of long/unparsed Retry-After deadlines.

`python -m unittest discover -s tests -v`: 19 end-to-end tests passed in approximately 22 seconds after final engine changes. Cases cover parallel ranges, range-ignore/weak-validator fallback, unknown-length single request, manual redirects, changed resources, malformed ranges, unexpected encoding, truncated transfers, numeric Retry-After, pause/resume extent reuse, process-kill recovery, corrupted extents, raced destination collision, digest mismatch, engine ownership, cancellation, protected signed URLs and future database schema rejection.

`cargo clippy --workspace --all-targets --offline -- -D warnings`: passed. The restricted filesystem emitted incremental-cache hard-link warnings, unrelated to Rust/Clippy source diagnostics; compilation continued using copies.

Tests use generated ~3 MiB files served only on 127.0.0.1. Every successful result is independently hashed. On Windows, successful output is checked for ZoneId=3. CLI processes use isolated state and output directories.

Sandbox restrictions required the HTTP suite to run with loopback network access. Early sandbox-only runs were environmental failures and are not counted as successful evidence. A Python fixture database handle was explicitly closed to permit Windows cleanup.

No public-site compatibility, 8K media, real power-loss safety, >4 GiB transfer, HTTP/2 negotiation, installation, update, antivirus scanning, accessibility or acceleration performance claim is established by these results.

## Final engine and desktop verification

After lazy extent scheduling, origin throttling, redirect-body bounding and pause-during-verification changes, the 9 unit tests and 19 HTTP tests passed again. The last HTTP run took approximately 63 seconds while desktop builds were also active; this is regression evidence, not a throughput benchmark.

`npm run build` in apps/desktop passed TypeScript checking and production bundling. `cargo build --manifest-path apps/desktop/src-tauri/Cargo.toml --features custom-protocol --locked --offline` produced the Windows x64 standalone preview. Frontend assets are bundled locally; no running development server is required. Rust and npm lockfiles are retained.

Native interface QA exercised the compiled app. Verified empty state, new-download form, URL/destination/hash input, queuing, starting, active-state controls, close/reopen and persistent completed history. The file was generated by tests/serve_fixture.py, had 3,145,737 bytes and SHA-256 `dae24d431738491859c04ca5fab6b5694883e22083f782456e15a4734bb96281`, and was independently hashed after completion. No public content or account was used.

The window was closed after an active transfer was observed and reopened with completion recorded. This is a native lifecycle smoke test, not exhaustive close/crash timing qualification. Full pause/cancel native click-through, save-dialog, accessibility and clean-machine tests remain open; engine pause/cancel behavior is covered by the HTTP suite.

## Queue/browser/release foundation verification

`scripts/test.ps1 -Faults -Protocols` passed after the static VCRuntime change: 13 Rust tests, 33 passing Python fixture methods (the optional resource method is skipped in this invocation) and 2 Node extension tests. Python fixtures took approximately 54 seconds on the last complete run; this is regression evidence, not a benchmark. TypeScript/Vite production builds and root/native Clippy with warnings denied passed. The fixture dependency environment used h2 4.3.0, hpack 4.2.0, hyperframe 6.1.0 and cryptography 50.0.2; none are shipped.

Additional cases cover priority order, a future start time, global queue pause/requeue, explicit-pause exclusion, named-queue rotation after a newly durable extent, sequential in-flight progress, v1 migration/backups, v2 idle-lock migration, persistent numeric/HTTP-date origin deadlines, bounded/deduplicated batch import, a failed storage write, durable/idempotent native handoff, origin checks and malformed/oversized/truncated/unknown-field protocol inputs. The extension tests verify explicit context-menu-only enqueueing, rejection of credential/scheme inputs, acknowledgement matching and source-free local status.

The fault build abruptly exits without destructors at `after_body_write`, `after_extent_flush`, `before_extent_commit`, `after_extent_commit`, `after_publication_intent`, `after_origin_metadata`, `after_rename` and `before_completion_commit`. Each then resumes with the ordinary build and checks the final generated bytes/hash/origin metadata. These are eight subcases inside one fixture method. Fault exit, short quantum and private test-CA hooks are compiled only with `fault-injection`, and excluded from the ordinary installer engine. This is process-loss testing, not hardware power-loss simulation.

TLS qualification uses an ephemeral private CA, unique issuer, signed CRL served on loopback and an h2-only ALPN TLS server. The positive ranged download and negative untrusted, expired and wrong-host cases pass. The test-only binary trusts only its supplied CA file; peer/hostname/revocation checking stay enabled and no Windows trust settings are edited.

## Real size/path fixture

An optimized engine downloaded and independently SHA-256-verified **4,294,967,553 bytes** through a **397-character Unicode path**, with 64-bit decimal history counters and no-overwrite publication. The strengthened fixture generates a distinct SHA-256-derived pattern per 64 KiB block, incorporating high offset bits, so wrapped/misplaced writes cannot pass as they could with an all-zero preallocated file. Hash: `f69b5a49cb06ef8cfb5c521d994afe33b74dbb0358fd15e8d56dbc3a2cbba46e`. The file was removed with its isolated temporary test folder. The recorded transfer/verification elapsed time was 242.45 seconds under other build/test load, not a performance benchmark. Evidence is in `docs/evidence/resource-evidence.json`. An earlier all-zero fixture also passed but is not the final offset-integrity evidence.

An earlier debug/loaded-machine resource attempt timed out; a later interrupted fixture run also hit a subprocess deadline after a long execution interruption/delay whose cause was not qualified. Those are not counted as passes. The stable optimized resource run and subsequent complete ordinary suite passed. This does not qualify disk-full behavior, filesystem/reparse races, every large-file size or physical power-loss safety.

## Installer and inventory

`scripts/build.ps1 -Bundle` produced a current-user x64 NSIS installer. PE import inspection found an external VCRUNTIME140 dependency in the first CLI build; the CLI now applies `static_vcruntime::metabuild`, matching the desktop's approach. Subsequent imports contain Windows/UCRT dependencies and no external VCRUNTIME140 DLL. The full engine suite passed after this linkage change. A developer-machine isolated install contained both executables, extension/setup resources and uninstall program; the installed CLI doctor passed.

The installed native app opened and its accessibility tree exposed the existing completed history plus queue limit, Start queue and Theme controls. The Windows helper returned `failed to activate captured window` on initial and refreshed-window activation, so no successful updated native click-through/visual claim is made yet. Original preview UI smoke evidence above remains historical. Uninstall, clean-machine, upgrade, browser UI/store, signed update and full accessibility qualification remain open.

The generated development CycloneDX inventory includes 353 resolved/embedded/platform/installer components, 516 collected root notice files and 44 entries needing further notice review. Some missing files are optional packages for other platforms. This inventory is broader than the runtime and is not a completed licence audit. Python/media helper binaries are not in the Core installer; compiler/runtime, native source, WebView2 and NSIS terms still need release review.

The inventory was validated with jsonschema 4.26.0 against the official CycloneDX 1.6 BOM/SPDX/JSF schemas, with zero schema errors. This checks structure, not licence clearance or exact runtime-only completeness. The validator and schemas were workspace-only development tools.

The actual installed `idmxl.exe` also passed four selected end-to-end cases: conditional ranges, protected/redacted signed URL, durable native-host/private-network policy, and pause/resume reuse. These repeat four existing methods against the installed artifact rather than increasing the count of distinct test cases.

## Opt-in adaptive experiment

After adding the experimental CLI controller, the full suite passed again: 16 Rust tests, 36 ordinary Python methods plus the separately passed resource method, and 2 Node cases (55 distinct top-level cases in total). The ordinary Python invocation reports 37 methods with the resource method skipped; that resource result is recorded above. New unit cases cover multi-sample bounds, non-improving trials/cooldown and sustained regression. Additional HTTP cases check adaptive bytes/hash, changed-identity rejection and preservation of the single-request one-use contract.

`scripts/benchmark-adaptive.py` compares fixed-one to adaptive-max-four on generated 16 MiB data, with an explicit artificial 524,288-byte/s limit per request. On Windows 11 build 26200, Intel64 Family 6 Model 142 Stepping 10 / 8 logical CPUs, observed times were 34.299 s and 14.331 s, peak outstanding body requests 1 and 4, with matching SHA-256 `341aacac661ccb210720bedaa9ead5d668fe5ea41a73532fc147c71e34040df1`. Only one warm run per mode was measured under development-machine load. The first fixture counter incorrectly counted already-finished responses during post-body sleep and was corrected before recording this evidence. This does not qualify shared-bandwidth/disk/HTTP2 tuning or establish a general/browser speedup. See `docs/evidence/adaptive-benchmark.json` for exact inputs/results.
