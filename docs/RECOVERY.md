# Automatic server recovery

IDMXL keeps resumable downloads in **Waiting for server** when the server returns
HTTP 429 or 503. It saves the cooldown and resumes automatically when the worker
is running and the server's deadline has passed. The desktop and browser popup
show the wait; **Pause** and **Cancel** remain available.

## Everyday use

- Keep the IDMXL queue running for captured and queued downloads. A paused queue
  stays paused. After reopening the app, start its queue if it was stopped.
- A download started individually also waits and resumes while its separate
  download worker is running. Closing the interface does not stop that worker.
- If the worker or PC stops during a cooldown, the saved waiting job remains in
  history. Reopening IDMXL with its queue running lets it resume when eligible.
- Pause a waiting job to prevent automatic resume. Cancel also stops automatic
  attempts and retains native partial data, following the existing controls.
- Set **Automatic recovery limit (hours without progress)** in a file's details
  to limit recovery. The default is 24 hours, with a maximum of seven days.
  Reaching the limit reports a failure while preserving saved data. **Retry now**
  starts a fresh recovery allowance. It retains the existing explicit, one-use
  override for a saved server wait; other jobs keep their cooldown.

Automatic replay applies to reusable native file URLs and reusable components
of supported clear HLS/DASH media. A one-use or uncertain URL is not silently
retried. Browser-assisted transfers continue to use the browser's recovery rules.

## Recovery policy

Valid `Retry-After` values support both delay seconds and HTTP dates, including
waits longer than five minutes. When the header is missing or invalid, cooldowns
start at five seconds and increase to ten, twenty and then up to 300 seconds,
with up to one second of random variation. A valid longer server delay takes
precedence. Automatic attempts never use the explicit **Retry now** override.

Throttling has its own persisted time budget. It does not exhaust the small
per-block budget used for interrupted transport requests. Newly saved progress
starts a new recovery episode. Remote identity is checked before reuse. A
continuously owned Windows session can retain its validated blocks and running
whole-file hash across a cooldown; its staging handle denies external writes
and deletion, and its saved extent records must still match. A new process or
an invalidated session rechecks saved block hashes in full.

Server cooldowns are shared by jobs on the same origin. Waiting releases the
engine lock, allowing an eligible job on another origin to proceed. Media
component waits are reflected on their parent download; finished components are
kept and hidden component jobs are not scheduled independently.

## Request pacing

New body requests normally have a 50 ms minimum spacing per origin. A throttling
response raises spacing to at least one second; further rejections double the
learned interval, up to 30 seconds, even when some progress continues. This
origin learning survives process restart and is separate from the job's
no-progress recovery allowance. After 64 successful responses and at least two
minutes beyond the last cooldown, the interval can decrease by one eighth.
Repeated throttling also lowers the concurrency ceiling to two at a four-second
interval and one at eight seconds. Successful recovery gradually restores the
configured ceiling. A media parent does not count its child's rejection twice.

For files from 32 MiB to less than 512 MiB, automatically sized body requests
shrink from up to 16 MiB to a 4 MiB minimum near completion. Files at least
512 MiB use requests up to 128 MiB. The final remainder can be shorter.
Smaller files retain 1 MiB requests. Recovery checkpoints stay at 1 MiB, and the
experimental CLI request-size override remains available for controlled tests.

## Diagnostics and tests

The CLI's `--metrics` option writes a bounded response history containing HTTP
status, request offset/length, timestamps, retry instructions, attempt number and
concurrency, plus recovery deadlines. Cooldown snapshots survive process loss.
The report contains no source URLs, filenames, cookies or raw response headers.

`--recovery-timeout-seconds` controls the direct CLI run's recovery allowance;
the queue uses each job's saved policy. The maximum is 604800 seconds.

`tests/test_recovery.py` sends real generated bytes and repeatedly rejects a
file's final bytes. It covers recovery beyond two retries, missing/invalid/date
retry instructions, persistent ten-minute cooldowns, process loss, Pause/Cancel,
time-budget expiry and another origin proceeding during a wait. Long-deadline
restart tests simulate elapsed time in an isolated database; separate tests
exercise real waits. Media tests cover a throttled segment and resumed assembly.

These checks establish the tested behaviors. They do not establish compatibility
with every server or a general speed advantage over another download manager.

## Measured qualification

The [22 October results](RECOVERY-RESULTS.md) include real public-server 429
recovery, verified 14 GB completions, a 21.47 GB process-loss test and isolated
update qualification. The recovery build completed reliably but was slower
than IDM in that public pair; timings and remaining speed priorities are retained.

The subsequent [speed update qualification](SPEED-RESULTS.md) records retained
validation tests and a fresh 14 GB pair where IDMXL completed in 26m57s versus
32m03s for IDM. That native public run used sequential mode; the separate
controlled rejection fixture measures the retained-validation change directly.
